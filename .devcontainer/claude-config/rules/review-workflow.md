# レビュー運用（コミット前の品質ゲート）

個人の意識に頼らず、**Claude が開発フローの中でレビューを自発的に実施する**。
ユーザーが「レビューして」と言わなくても、以下のタイミングで自分から動くこと。

## コミット前（必須・Claude が自動実施）

変更の規模に応じてレビューしてから commit する:

- **実質的なコード変更**（ロジック変更・新機能・バグ修正・複数ファイルの変更）
  → commit 前に code-review スキル（/code-review 相当）を実行する。
    スキルが使えない環境では、変更ファイルと影響範囲を読み直すセルフレビューで代替。
    CRITICAL / HIGH の指摘は**修正してから commit**。MEDIUM 以下は要約して報告し、ユーザー判断
- **セキュリティに触れる変更**（認証・入力検証・秘密情報の扱い・外部送信・決済・権限まわり）
  → 上に加えて /security-review（またはセキュリティ観点の subagent レビュー）を実行
- **軽微な変更**（typo・ドキュメント・設定1行・コメント）
  → レビュー省略可（過剰な儀式にしない）

## /security-review が動かないとき（コンテナ内で起こりうる）

/security-review は origin/HEAD に依存する。無い場合:

1. リモートに繋がるなら `git remote set-head origin -a` を実行して再試行
2. 繋がらないなら、subagent に「main（または master）との差分をセキュリティ観点で
   レビュー」と依頼して代替する（メインのコンテキストを消費しない利点もある）

## 磨き上げ（提案ベース）

動作確認まで済んだ機能の push / マージ前に、/simplify（リファクタ提案＋適用。
バグ探しではなく品質整理）をユーザーに**提案してよい**。勝手に適用はしない。

## 節目の深掘り（ユーザー手動・課金）

リリース前・大きな機能のマージ前には /code-review ultra（クラウド多エージェント監査）という
選択肢がある。**課金が発生し数分かかるため、Claude からは起動しない**。節目で選択肢として案内する。
引数なしで実行するとローカルブランチを bundle して送るため、GitHub リモート不要。

## PR レビュー（参考）

- 既存の GitHub PR は /review <PR番号>（gh 認証が前提）
- GitHub に繋がらない環境では `git fetch origin pull/<PR番号>/head:pr-<PR番号>` で取得し、
  ベースブランチとの差分レビューに切り替える

## 原則

- レビュー指摘は「直してから commit」が基本。ユーザーが急いでいる場合は指摘を要約して
  報告し、commit するかの判断を仰ぐ
- 自動修正（--fix 等）を使う前に、working tree に無関係な変更が混ざっていないか確認する
- 詳しい使い分けは guideline リポジトリの docs/REVIEW_COMMANDS.md を参照
