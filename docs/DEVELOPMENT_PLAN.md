# 開発計画書 — SMS文例検索ツール

作成日: 2026-09-15
元資料: 2026-09-15 社内ミーティング録画・文字起こし（米山／内田、〜50分10秒まで。以降は別話題のため対象外）、gnote BigQuery テーブル一覧・カラム一覧、テンプレート抽出サンプル（内田さん提供）
ステータス: 内田さんとの確認済み（2026-09-18 回答反映）。BigQuery のビュー提供待ちだった項目は解決、L3 のエンジニア相談記録の記入が残っている

## ① 要件

### 何を作るか

**「こういうSMSを送りたい」と思ったときに、過去に実際に送られた文例を探して、そのまま文章案にして、依頼まで出せる道具。**

今は、良い文例は人の記憶の中にしかない。Slackで「いい文章教えて」と聞いても3人からしか返事が来ない。
一方で、SMSの配信データ（どの文面を誰にいつ何通送ったか）は BigQuery（社内のデータ置き場）に全部入っている。
**記憶に頼っていた部分を、データで置き換える。**

副産物として、社内が把握していないクライアント自作のテンプレート（勝手に作って大量に送ってくれている良い文例）も見えるようになる。

### 対象ユーザー

| フェーズ | 対象 |
|---|---|
| Phase 1（今回） | **米山さん個人**。Dev Container 内でローカル起動して自分で使う |
| Phase 1.5 以降 | プランナー・ディレクター全員（社内配布） |

### 起動契機

プランナー・ディレクターが、クライアントへのSMS提案を作る場面（打ち合わせ準備中、クライアント同席中）。

## ② 実行基盤の判定

- **実行基盤: Dev Container（`container` プロファイル）**
- 採用理由:
  - BigQuery クライアントライブラリ等、npm 依存が必要（GAS では不可）
  - 顧客データに読み取りでアクセスするため、セキュリティ区分 L3 相当の統制（Dev Container・ファイアウォール・キーレス認証）が前提になる
- Phase 1 の実行場所: **Dev Container 内でローカル起動のみ**（Cloud Run へのデプロイ・IAP 認証は行わない）
- Phase 1.5 以降の実行場所: Cloud Run（`GCP_SELF_SERVICE_DEPLOY.md` の手順に従う）、IAP で社内ドメイン `inter-zone.jp` 限定

## ③ 依存の判定（2026-09-21 確定）

- npm 依存: **あり**（Webフレームワーク等。BigQuery クライアントは今回入れない。下記参照）
- 依存追加は Dev Container 内でのみ実施
- **検疫（`minimum-release-age`）は pnpm では実際に効いている**（2026-09-21、`package.json` 確定作業で実測）。当初「効いていない可能性が高い」としていたのは npm 側の話で、訂正する
  - `npm 10.8.2` → `min-release-age` は無視される（npm 11.10+ が必要。ここは訂正前の記述どおり）
  - `pnpm 10.34.5` → `pnpm config get minimum-release-age` が `10080`（＝7日）を返す。**有効**。`devcontainer.json` の `postCreateCommand` は `pnpm-lock.yaml` があれば pnpm を使うため、**本プロジェクトは pnpm ルート**
  - 実際に `pnpm install` 時、公開後2〜5日だった `prettier@3.9.8` と `eslint@10.11.0` が検疫で弾かれ、1つ前の成熟版（`prettier@3.9.6` / `eslint@9.39.5`）が解決された（実例）
  - **ただし「検疫＝後から足すと1週間待ち」ではない**。検疫は「追加を止める」のではなく「公開から7日未満のバージョンを候補から外す」フィルタで、pnpm は弾いた分を諦めて1つ前の版を**即座に**解決する。待ち時間が発生するのは「数日前に出たばかりの版が今すぐ必要」な場面だけ。この誤解が §③ 旧版の「BigQueryクライアントを今のうちに入れておく」という判断を歪めていたため、訂正して記録する
  - 使うライブラリを着手直後に確定させる方針自体は、検疫とは別に「後から構成を変える手戻りが大きい」という理由で維持する
- lockfile（`pnpm-lock.yaml`）は必ずコミットする

### 依存構成（確定）

コンテナは `node:20-slim`（Node 20.20.2）。この Node 20 制約により、**一部パッケージは最新メジャーではなく1つ前のメジャーに固定**している。

| 用途 | 採用 | 版 | 理由 |
|---|---|---|---|
| フレームワーク | **Next.js** | `^16.3.5` | 「伏せモードはサーバ側でマスクする」（§④）には API 側の処理が要る。画面と API を1つで持てる。Phase 1.5 の Cloud Run + IAP にそのまま載る |
| UI | **React / React DOM** | `^19.3.0` | Next 16 の peer |
| 入力値検証 | **zod** | `^4.6.5` | 検索・フィルターのクエリパラメータを境界で検証する |
| スタイル | **Tailwind CSS** | `^4.3.3` | 検索・フィルター・一覧のUIには十分。`npm-safety.md` の既知パッケージ |
| 型 | **TypeScript** | `^5.9.3` | 最新は 7.0.2（ネイティブ移植版）だが Next 16 との組み合わせ実績が薄いため 5 系に固定 |
| テスト | **Vitest** | `^4.1.11` | **v5 は Node >= 22 必須のため 4 系に固定**。マスク処理・分類辞書の単体テスト用 |
| Lint | **ESLint** | `^9`（`9.39.5`） | `eslint-config-next` 自体の peer は `>=9.0.0` で緩いが、その先の `eslint-plugin-import` 等が **まだ ESLint 10 系に対応していない**（`pnpm install` で unmet peer 警告を実測）。ESLint 10 系は使わず 9 系に固定 |
| Lint（Next用ルール） | **eslint-config-next** | `^16.3.5` | |
| フォーマット | **Prettier** | `^3` | |
| パッケージ管理 | **pnpm** | `10.34.5` | Dockerfile で corepack 経由で有効化済み |

**あえて入れないもの**:
- **データベース（SQLite 等）** — テンプレートは1万件規模。キャッシュしたJSONをメモリ上で配列フィルタすれば足りる。DBを増やすと依存も運用も増える
- **`@google-cloud/bigquery`** — Phase 1 の当面の目標は「営業メンバーに見せる画面モックアップ」（ダミーデータで可）であり、BigQuery接続は本計画の対象外。§⑤の構成図のとおり、BigQueryに触るのは「SQLを1本流してJSONに落とす」スクリプト1本だけで、アプリ本体はそのJSONを読むだけなので、後から足しても画面側のコードには影響しない。接続情報が届いた時点で `^8.3.1`（Node 20 対応。v9 は Node 22 必須）を足すか、gcloud 同梱の `bq` コマンドで代替するかを判断する
- **UIコンポーネントライブラリ** — Tailwind で足りる

### Node 20 が最新メジャーを弾いている件（別課題）

`vitest`（v5 は Node >= 22 必須）、`@google-cloud/bigquery`（v9 は Node >= 22 必須）など、Node 20 だと最新メジャーが使えないパッケージが複数ある。Dockerfile にも「pnpm 11 は Node 22.13+ 必須なので 10 に固定」とあり、Node 20 は意図的な選択。`npm-safety.md` の推奨環境は Node 24 + npm 11 であり、テンプレート側の Node を上げれば解消するが、`.devcontainer/` の正本は guideline リポジトリのため本プロジェクト単独では判断しない。

## ④ 外部接続

- 使用する外部 API: **BigQuery**（**`gnote-analytics.gnote_sms_catalog`（asia-northeast1）のビュー5本**。2026-09-18 に内田さんが本件専用に作成）
  - 当初は生テーブル `gnote_jty_prod` の6テーブルに直接アクセスする想定だったが、**生テーブルへの権限は付与されていない**。SMS文例に必要な範囲だけを切り出したビュー越しにアクセスする
  - ビューの構成: 文面／配信設定／配信バッチ／送信結果／テンプレート別実績
  - 「よく送られている順」は `vw_sms_template_usage` を `send_count` の降順に並べるだけで出る
- 接続方式: サービスアカウントキーは使わない。`gcloud auth login` ＋ `GOOGLE_IMPERSONATE_SERVICE_ACCOUNT` によるキーレス impersonation（`GCP_INTEGRATION_GUIDE.md` の標準手順）
- 必要な権限（最小スコープ）: **上記ビュー5本の閲覧権限 ＋ クエリ実行権限**。テーブル作成権限は不要（内田さん確認済み）
  - 生テーブル（`nskn_customers` 等の個人情報本体を含む）へのアクセス権は持たない。ビューが権限の境界そのものになっている
- **`.devcontainer/` への本プロジェクト固有の変更**（2026-09-18 実施）:
  - `init-firewall.sh` の `REQUIRED_DOMAINS` に `bigquery.googleapis.com` と `iamcredentials.googleapis.com` を追加。後者は impersonation（権限の借用）に必須で、無いと認証は通るのにクエリ直前で失敗する。認証に使う `oauth2.googleapis.com` / `accounts.google.com` は `OPTIONAL_DOMAINS` に既出
  - `Dockerfile` に Google Cloud CLI（gcloud）を追加。鍵ファイルを置かない方針のため、利用者本人が都度認証するのに必要。クエリ実行自体は Node のライブラリが行う
  - ⚠️ **`.devcontainer/` の正本は guideline リポジトリの `templates/`**。`sync-template.sh --apply` を実行すると上記2つは**上書きされて消える**（`.bak` は残る）。BigQuery は全プロジェクト共通の要件ではないためテンプレート側には入れない。同期を実行したら、この2箇所を復元すること
- 扱うデータの分類: **L3 確定**（2026-09-15 トリアージ実施。`.security-level=3`、`docs/triage-record.md` 参照）
- L3 プロセス: Slack `#ai-jigyobu-engineer-consult` で相談済み（2026-09-15 投稿 → 2026-09-18 内田さん回答）。`docs/engineer-consultation.md`（6項目・有効期限つき）の記入が開発開始の前提
- 社外の人が書いた文章が入る項目: **あり**（SMS本文はクライアント作成のものを含む）
  - **⚠ 本文そのものに個人情報が混ざっている**（2026-09-18 内田さんが実データで確認）:
    - **実在のお客様の氏名が直書きされたもの 511件**（全11,010件中）。差し込み変数を使っているのは56件だけで、大半は店舗が手で打ち込んだ固定文 → **ビュー側で「〇〇様」に伏せ済み・伏せ漏れ0件**
    - **本文中の電話番号 2,784件** → ビューでは伏せていない。店舗の連絡先と推測されるが未確認（§⑧の確認事項）
    - **ナンバーらしき記載 22件** → ビューでは伏せていない。`has_platelike` が true の行を除外して回避する
  - **設計上の教訓**: 「顧客マスタに触らなければ個人情報は入らない」は成立しなかった。テーブル構造（列の参照関係）だけを見て安全と判断してはいけない。**自由記述の列は中身を実データで確かめる**
  - マスク方針: クライアント同席用の「伏せモード」で、会社名・店舗名の列だけでなく**本文中に直接書かれた店舗名・電話番号・URLもマスクする**（本文に「車検のコバック岡山円山店です」のように直書きされているケースがあるため、列を隠すだけでは不十分）。マスクは画面側ではなくデータを渡す側（サーバ）で行う（DevTools・コピー経由の漏洩を防ぐ）

## ⑤ 設計

### 構成

```
[BigQuery: gnote-analytics.gnote_sms_catalog（ビュー5本）]
        │ 1回のSQL実行（Phase 1は毎回叩かない）
        ▼
[ローカルにキャッシュしたテンプレート一覧]
        │
        ▼

```

- Phase 1 は BigQuery を毎回叩かない。テンプレートは1万件規模なので、SQLを1本流してローカルに落とし、アプリはそれを読む
- Phase 1.5 以降、全員配布時に日次のスケジュールクエリへ切り替える

### データの取得経路（2026-09-18 内田さんが実データで検証済み）

生テーブルの結合は**内田さんがビュー側で済ませてくれている**ため、アプリ側は以下を読むだけでよい。

| ビュー | 中身 |
|---|---|
| 文面 | テンプレート本文（氏名は「〇〇様」に伏せ済み）・設定内容 |
| 配信設定 | いつ・どのテンプレートを使うか |
| 配信バッチ | 実際の配信処理 |
| 送信結果 | 宛先ごとの到達結果・通数 |
| `vw_sms_template_usage` | **テンプレート別の送信実績**。`send_count` 降順で「よく送られている順」 |

**✅ 解決済み（旧・最優先未検証事項）**: 「送信実績の結合が実データで成立するか」は内田さんが検証し、**顧客マスタを経由せずに集計できることを確認済み**。送信実績のあるテンプレートは **6,963件**、最多で **53,116通**。Phase 1 の看板機能は成立する。

**✅ 解決済み（旧・結合済みテーブルの要否）**: ビュー方式で決着。テーブル作成権限は不要。

**⚠ 母数の不一致（要確認）**: カラム一覧では `nskn_shortmail_templates` は **15,006件**だが、内田さんの調査報告は**全11,010件**が母数。差の約4,000件が何か（削除済みの除外か、SMS本文が無いメール専用テンプレートの除外か）は未確認。**未分類を隠さない**という設計方針（後述）に関わるため確認する。

### リマインド側も対象に含められる見込み（2026-09-18 更新）

当初は「リマインド側の文面テンプレートが BigQuery に無い」と判断し Phase 1 を受注側のみとしていたが、**内田さんの調査では同じテーブルに入っていそう**とのこと:

- テンプレート名に「入庫・前日・リマインド・予約・来店」を含むもの **1,217件**
- 入庫予約用URL（`nyk_reserved_url`）が設定されたもの **3,593件**

受注側とリマインド側が同じテーブルに混在しているため、**分類（§後述）でどう切り分けるかが論点**になる。MTG でも「リマインドに見せかけた受注の可能性がある」という話が出ており、名前だけの判定では危うい。`nyk_reserved_url` の有無と組み合わせて判定する。

Phase 1 のスコープに含めるかは、実データを見てから判断する（含められるなら含める。文例集としての価値が上がるため）。

### 分類（検索の絞り込み軸）の作り方

**課題**: 「利用シーン」「車検」「フランチャイズ」「店舗」で絞り込みたいが、それを表すカラムが存在しない。「車検5ヶ月前」「12ヶ月点検」といった情報はテンプレート名と本文の自由記述にしかない。会社名が「西崎自動車」なのに本文が「車検のコバック岡山円山店です」というケースが普通にあり、フランチャイズは本文からしか読めない。

**方式: 辞書＋正規表現で機械的に付ける（Phase 1）**。AIによる分類はPhase 1.5に回す（外部送信先が増えるとセキュリティ区分の再判定が必要になり、Phase 1の足を止めるため）。

初版辞書の案:
- 利用シーン: `車検誘致` / `車検お礼` / `車検証準備` / `12ヶ月点検` / `6ヶ月点検` / `18ヶ月点検` / `3ヶ月点検` / `オイル交換` / `タイヤ` / `コーティング` / `車販・乗り換え` / `キャンペーン・セール` / `長期休暇案内` / `LINE・アプリ誘導` / `予約リマインド`
- タイミング: 本文・名前の「◯ヶ月前」「満了日まであと◯ヶ月」を抽出
- フランチャイズ: 本文中の `車検のコバック` / `車検の速太郎` / `ENEOS` / `宇佐美` / `ピットボーイ` などを検出
  - ※ 会社名の接頭記号（`C252_` 等）は請求先IDベースの旧採番で、現行は数字のみのため使わない。kintone の請求先マスタとの接続もスコープ外（§⑧解決済み参照）
- 社内作成かクライアント作成か: `【IZ_` 接頭辞と作成者IDで判定
- SMSの型: `nyk_reserved_url` が入っていれば「入庫連動」、なければ「テキスト型」

設計上の注意:
- **未分類を隠さない**。余計な文例が混ざるのは目で捨てられるが、拾えなかった文例は「そんな事例は無い」と誤認させ、提案の質が静かに落ちる。タグは絞り込みより「入口と並び替え」として設計し、未分類も件数付きで見せる
- **辞書をコードの中に埋めない**。リポジトリのJSONに置くと更新依頼が米山さんに集中する。スプレッドシート等、後で自分以外も触れる場所に置ける形にする

### データの汚れへの対応

| 症状 | 実例 | 対応方針 |
|---|---|---|
| テスト用が大量に混ざる | 「配信テスト」「テスト」「わ～」「ありがとー！」 | 既定で除外。チェックで表示可 |
| テンプレート名が空 | クライアントID 587 など | 本文の先頭を見出しに使う |
| 会社名が空 | 古いクライアントID（218, 446, 493 等） | クライアントIDで表示 |
| 中身が同じで店舗名・電話番号だけ違う | コバック各店の同型文面 | 名寄せして合算（Phase 1.5） |
| **本文に実在のお客様の氏名が直書き** | 511件（差し込み変数利用は56件のみ） | **ビュー側で「〇〇様」に伏せ済み**（内田さん対応・伏せ漏れ0件）。アプリ側の追加対応は不要 |
| **本文に電話番号が直書き** | 2,784件 | **店舗の連絡先という前提**（SMSはテンプレートの一斉予約送信が主用途で、個別連絡には使いにくいため／米山判断 2026-09-18）。ビューでは伏せず、**伏せモードでアプリ側がマスクする**。ただし接続後にクエリで裏を取る（§⑧） |
| **本文にナンバーらしき記載** | 22件 | ビューの `has_platelike` が true の行を**既定で除外**する |

### 受け入れ条件（Phase 1）

- [ ] テンプレート（1万件規模。受注側／リマインド側の切り分けは実データを見て判断）が検索・一覧表示できる
- [ ] キーワード（本文・テンプレート名の全文検索）＋ 絞り込み（クライアント／フランチャイズ／利用シーン／車検何ヶ月前／SMSの型／使用中のみ）で絞れる

### 文字数・通数・料金の仕様（申請書『【配信文章設定】…』より転記）

米山タスクだった「現行申請書の書式を `materials/` に配置する」が完了し、実物（`【配信文章設定】請求ID_クライアント名…xlsx`）から数式を移植した。**申請書は `materials/` 配下で git 管理外**（`.gitignore` 済み）のため、仕様をここに転記して残す。

**通数・料金**（`［SMS】配信料金表` シート）:

| 文字数 | 通数 | 料金/件 |
|---|---|---|
| 70文字まで | 1 | 25.0円 |
| 71〜132文字 | 2 | 35.0円 |
| 133〜198文字 | 3 | 45.0円 |
| … 66文字ごとに +1通・+10円 … | | |
| 595〜660文字 | 10 | 115.0円 |
| 661文字以上 | — | 「660文字以内に調整してください」 |

数式: `通数 = 70文字以下なら1、それ以外は ROUNDUP(文字数 / 66, 0)`。`料金 = 25 + (通数-1) × 10` 円/件。

**文字数の数え方は SMSの型ごとに異なる**（`【SMS】テキスト` / `【SMS】入庫連動` / `【SMS】リマインド` の各シートより）:

| 型 | 数式 | 改行 | URL |
|---|---|---|---|
| テキスト | `LEN(CLEAN(本文)) + 改行数 × 2` | 2文字 | — |
| 入庫連動 | 同上 **+ 36文字** | 2文字 | 入庫予約URLが36文字で本文末尾に自動挿入される（途中挿入は不可） |
| リマインド | 置換後の文字数（下記置換表） | **1文字** | — |

`CLEAN()` は改行を除去する関数。**リマインドは70文字・1通のみ**（料金表の注記: 「リマインド配信は70文字までの配信のみとなります」）。

**リマインドの置換表**（`【SMS】リマインド` シートより）:

| 置換元 | 置換先 | 文字数 |
|---|---|---|
| `@customer_name@` | お客様名 | 15 |
| `@shop_name@` | 店舗名／工場名 | 11 |
| `@work_name@` | 作業種別名 | 11 |
| `@visit_date@` | 来店日時 | 12 |
| `@reserve_change_url@` | 予約変更URL | 20（`@` 前にスペースが無いとリンクが壊れるため注意） |

**申請書の入力項目**（依頼文パネルはこれに寄せる）: `作業内容`（追加／修正／停止）・`停止状態`（3択）・`テンプレート名`、入庫連動のみ ＋`URL種別`／`作業種別名・作業グループ名`／`店舗名・工場名`。

**⚠ §⑧ 未決事項との関係**: 「11月の長文対応リリース後の仕様」は、この表の660文字・10通・115円が現行の上限として既に定義されている。長文対応で拡張される可能性があるのはこの表自体か、あるいはリマインド側の70文字制限かのどちらか（または両方）。断定はできないため §⑧ の未決事項として引き続き残す。
