description: 新規プロジェクト開始前の PII リスク・トリアージ（3問の対話形式）
---

あなたはこれから利用者と一緒に **PII リスクのトリアージ**を実施します。
配布対象は営業 / HR / コールセンター等の **非エンジニア**。専門用語を使わず対話形式で 3 問を順に聞き、判定結果を `.security-level` と `docs/triage-record.md` に書き出してください。

## 流れ

1. 「これから新しく作るシステムについて、3 問だけ確認させてください」と冒頭で伝える
2. 既存の `.security-level` がある場合: 「現在のレベルは X です。変更すると admin の承認が必要なので、注意してください」と警告
3. 1 問ずつ順に聞き、回答を待つ（一気に全問出さない）
4. 全部答えてもらったら判定 → ファイル作成
5. L3 なら必須プロセスを案内

## 質問

### Q1. 個人を特定できる情報を取り扱いますか？

下のチェックリストを読み上げ、「1 つでも該当するなら『はい』」と聞く:

```
☐ お客様の氏名・メール・電話・住所
☐ お客様の顔写真・身分証画像・名刺画像
☐ お客様の通話録音・声
☐ お客様の問い合わせ内容・対応履歴
☐ 社員の氏名 + 給与・評価・勤怠・健康情報
☐ クレジット情報・銀行口座
☐ パスワード・ログイン認証情報
☐ 個人情報や社内機密にアクセスできる API キー（read-only でも該当）
```

API 判定の補足（聞かれたら答える）:
- 「そのキーで何が読める / 書けるか」で判断
- 該当: Slack DM 履歴取得、Drive 全社閲覧、Gmail 読取、顧客 DB / HR / 売上アクセス、書込権限を持つ API
- 非該当: Slack 通知のみ、Google Calendar 自分の予定参照、公開ドキュメント取得、汎用 webhook

除外（聞かれたら答える）:
- 商品写真・UI スクショ・効果音
- 社員番号「だけ」（氏名・給与と紐づけない単独利用）

**利用者が迷っている場合は必ず「はい」（L3 に倒す）と案内する**こと。

### Q2. 社外の人（お客様）が直接使うシステムですか？

「顧客向け Web フォーム、予約サイト、顧客アプリ → はい」「社内のみで使う → いいえ」と例示。

### Q3. お金が絡みますか？

「決済 / 振込 / 送金 / クレジット情報の通り道 → はい」
「金銭にすぐ換算できる権限（割引コード発行 / ポイント付与 / 在庫増減）→ はい」

## 判定

- 1 つでも「はい」 → **L3**
- すべて「いいえ」 → **L1**

## ファイル作成

### `.security-level`
プロジェクト直下に作成。中身は `1` または `3` のみ（1 行）。

### `docs/triage-record.md`
プロジェクト直下の `docs/` に作成（無ければディレクトリも作る）:

```markdown
# トリアージ記録

## 日時
<今日の日付 YYYY-MM-DD>

## 回答者
<利用者に名前 or GitHub username を聞いて記入>

## 質問への回答
- Q1. 個人を特定できる情報を取り扱う？ → はい / いいえ
  - 該当した項目: <該当ありなら箇条書き>
- Q2. 社外の人（お客様）が直接使う？ → はい / いいえ
- Q3. お金が絡む？ → はい / いいえ

## 判定
.security-level = <1 or 3>

## 次のアクション（L3 の場合のみ）
- [ ] Slack #ai-jigyobu-engineer-consult で相談
- [ ] docs/engineer-consultation.md を作成・必須 6 項目埋め
- [ ] 上記が揃ってから開発開始

## 再トリアージが必要な変更
以下が PR に含まれる場合は `/triage` を再実施:
- 新規 API 接続（.env に新規 KEY / OAuth scope 追加）
- 外部送信先追加（Slack webhook / Twilio / Stripe / SendGrid / AWS SES 等）
- 書込権限の追加（read-only → write）
- DB スキーマ変更（テーブル追加 / カラム追加）
```

## 完了時のメッセージ

### L1 判定だった場合
```
判定: L1（社内のみ・PII なし）
AI 事業部内で進めて OK です。
今後、以下のいずれかを追加することになったら /triage を再実施してください:
- 新規 API 接続 / 外部送信先追加 / 書込権限追加 / DB スキーマ変更
```

### L3 判定だった場合
```
判定: L3（PII / 社外公開 / 金銭が関与）
以下のステップを完了してから開発開始してください:

1. Slack #ai-jigyobu-engineer-consult で「L3 案件相談」と投稿
2. AI 事業部のエンジニア担当が設計を見る → 助言をもらう
3. docs/engineer-consultation.md を作成し 6 項目を埋める:
   - 対象データ / 外部送信先 / 必要権限 / 想定事故 / 許可範囲 / 有効期限

CI（security-gate）が docs/engineer-consultation.md の記入と有効期限を検査します。
未整備の状態で main にマージしようとすると CI が止めます。
```

## 注意事項

- 利用者は非エンジニア前提。「permissions」「scope」「endpoint」等の英語専門用語を避け、日本語で言い換える
- 「ちょっとだけだから」「テストだから」で L1 に倒そうとする利用者がいたら、**「迷ったら上に倒す」「事故が起きてからでは遅い」**と説明
- 既存の `.security-level` を変更する場合は警告を出す（admin 承認の必要性）
